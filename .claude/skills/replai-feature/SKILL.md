# Replai Feature 오케스트레이터

Replai 프로젝트의 기능 개발 요청을 받아 pm-agent, feature-builder, db-agent, ai-builder, qa-agent를 조율하여 완성도 있는 구현을 만든다.

## Phase 0: 컨텍스트 확인

작업 시작 전 `_workspace/` 디렉토리 존재 여부를 확인한다.

- `_workspace/` 없음 → **초기 실행**: Phase 1부터 진행
- `_workspace/` 있음 + 부분 수정 요청 → **부분 재실행**: 해당 에이전트만 재호출
- `_workspace/` 있음 + 새 기능 요청 → **새 실행**: 기존 `_workspace/`를 `_workspace_prev/`로 이동 후 Phase 1부터 진행

## Phase 1: 요청 분석 및 스펙 결정

요청 유형을 파악하고 작업 경로를 결정한다.

**아이디어/기획 단계 요청** ("이런 기능 어떨까", "~하면 좋겠다", "아이디에이션"):
→ pm-agent를 서브 에이전트로 호출하여 스펙 문서 작성
→ 스펙 완성 후 사용자에게 확인 요청
→ 확인 후 Phase 2로 진행

**구체적 구현 요청** ("~컴포넌트 만들어줘", "~API 라우트 추가해줘"):
→ pm-agent 생략, Phase 2로 바로 진행

**판단 기준:**
- 구현 대상(컴포넌트명, 화면, 기능명)이 명확하면 → 구체적 구현 요청
- 그 외 → 아이디어/기획 단계 요청

## Phase 2: 작업 분해 및 병렬 실행

요청을 다음 영역으로 분해하고 해당 에이전트를 호출한다.

```
필요한 에이전트만 호출한다. 모든 에이전트를 항상 호출하지 않는다.

UI/로직 변경    → feature-builder (model: "opus")
DB 스키마 변경  → db-agent (model: "opus")
AI 에이전트     → ai-builder (model: "opus")

DB + UI가 동시에 필요한 경우 → 병렬 호출 (run_in_background: true)
순서 의존성이 있는 경우 (예: DB 스키마 확인 후 UI 구현) → 순차 호출
```

중간 산출물은 `_workspace/{phase}_{agent}_{artifact}.md` 에 저장한다.

## Phase 3: QA 검증

구현 완료 후 qa-agent를 호출하여 검증한다.

```
Agent(qa-agent, model: "opus") {
  검증 대상: [Phase 2에서 생성/수정된 파일 목록]
  확인 포인트: [각 에이전트가 명시한 검증 요청 항목]
}
```

qa-agent가 문제를 발견하면:
- 심각도 높음 → 담당 에이전트에게 즉시 재할당하여 수정 후 재검증
- 심각도 중간/낮음 → 수정 사항을 목록화하여 사용자에게 보고

## Phase 4: 결과 보고

사용자에게 다음을 보고한다:

```
## 완료

### 생성/수정된 파일
- [파일 경로]: 변경 내용

### DB 변경
- 마이그레이션 파일: 있음/없음
- 적용 방법: (있는 경우)

### QA 결과
- 통과: [항목]
- 주의: [있는 경우]

### 다음 단계
- 사용자가 해야 할 것 (있는 경우)
```

## 에러 핸들링

- 에이전트 호출 실패 → 1회 재시도. 재실패 시 실패 이유를 명시하고 사용자에게 보고
- 스펙 불명확 → pm-agent를 통해 구체화하거나 사용자에게 질문
- QA에서 수정 불가 문제 발견 → 사용자에게 기술적 제약 설명 후 대안 제시

## 테스트 시나리오

**정상 흐름:**
"인터뷰 세션 목록에 태그 필터 기능 추가해줘"
→ feature-builder가 SessionTable 컴포넌트 수정
→ qa-agent가 타입/보안 검증
→ 완료 보고

**에러 흐름:**
"인터뷰 중에 유튜브 영상도 분석해줘"
→ pm-agent가 MVP 범위 초과 판단
→ v2+ 항목으로 분류하고 현재 가능한 축소 버전 제안
→ 사용자 확인 후 진행 또는 중단
